1.2c) What does the yield keyword do in selection_sort()?
yield pauses the function and hands a value back to whatever asked for it (here,
a pair of indices). The function does not end. It remembers where it stopped and
keeps all of its variables (i, j, min_idx), and the next time a value is requested
it continues from the line right after the yield. This lets us run the sort one
step at a time instead of all at once.

1.2d) Relationship between selection_sort() and get_next_step()?
selection_sort() is a generator. restart() calls it and stores the resulting
generator in self.alg_method. get_next_step() calls next() on that generator, which
runs selection_sort() until its next yield and returns the yielded pair of indices,
which get_next_step() saves as self.outer_idx and self.inner_idx. So each call to
get_next_step() performs exactly one step of the sort. When the sort finishes,
next() raises StopIteration, and get_next_step() resets both indices to -1.

1.2e) What arguments does draw() take, and when are they updated?
The handout says two arguments, but in display.py draw(self, array, outer_idx=-1,
inner_idx=-1) takes three: the array to draw, and the two indices to highlight (the
outer index is drawn blue and the inner index is drawn red). The indices are updated
in get_next_step() each time the generator reaches a yield, and the array is changed
directly by the sorting algorithm as it swaps items. After calling get_next_step(),
controller.py immediately calls draw() with the current array and indices (on a
right-arrow/L key press, or on every cycle when Space "continuous" mode is on), so
the window always shows the most current step.


PART 2: Analyze Selection Sort

2.2a) High-level approach / why is it called selection sort?
Selection sort repeatedly SELECTS the smallest item in the unsorted part of the list
and swaps it into the next open position at the front. After the first pass the
smallest item is first, after the second pass the second smallest is second, and so
on until the whole list is sorted.

2.2b) Time complexity and how to tell from the code
O(n^2). selection_sort() has a for loop over i that runs n times, and inside it a
for loop over j that scans the rest of the list (up to n items). Nested loops that
each depend on n give about n + (n-1) + ... + 1 = n(n+1)/2 comparisons, which is
O(n^2). This is true even if the list is already sorted, because it always scans the
whole unsorted part.

2.2c) Space complexity and how to tell from the code
O(1). The code only swaps items inside the existing self.array and uses a few
variables (n, i, j, min_idx). It never creates a new list, so the extra memory does
not grow with the size of the input.


PART 3: Analyze and Implement Insertion Sort

3.1a) High-level approach / why is it called insertion sort?
Insertion sort goes through the list one item at a time and INSERTS each item into
its correct place among the items to its left, which are already sorted. It is like
sorting a hand of playing cards: you pick up a card and slide it left until it sits
in the right spot.

3.1b) Time complexity and how to tell from the pseudocode
O(n^2). The for loop runs n times, and the inner while loop can run up to i times
for each item (worst case, a reverse-sorted list, where every item must move all the
way to the front). A loop nested in a loop gives O(n^2). In the best case (already
sorted) the while loop never runs, so it would be O(n), but Big O describes the
worst case.

3.1c) Space complexity and how to tell from the pseudocode
O(1). It sorts in place by swapping neighbors and only needs the extra variables i
and j, so no additional storage grows with the size of the list.


PART 4: Analyze and Implement Bubble Sort

4.1a) High-level approach / why is it called bubble sort?
(The handout says "insertion sort" here, but it means bubble sort.) Bubble sort
repeatedly walks through the list comparing each pair of neighbors and swapping them
if they are out of order. On each pass the largest remaining item gets carried to
the end, like a bubble rising to the top of water, which is where the name comes from.

4.1b) Time complexity and how to tell from the pseudocode
O(n^2). There is an outer loop that runs about n times and an inner loop that runs
up to about n times for each of those, so the number of comparisons is about
n^2 / 2, which is O(n^2).

4.1c) Space complexity and how to tell from the pseudocode
O(1). It swaps items in place and only uses the loop variables i and j, so no extra
storage grows with the input size.

4.3) Why can we use "length(A)-1-i" and still get the same output?
Each pass of the outer loop carries the largest remaining item to the end of the
unsorted part. After pass i, the last i+1 items are already the largest ones and
sit in their final positions. Comparing items in that sorted tail can never cause a
swap, because they are already in order and are all bigger than everything before
them. So skipping them with "-i" gives exactly the same result with fewer
comparisons.

    def bubble_sort(arr):
        n = len(arr)
        for i in range(n):
            swapped = False
            for j in range(0, n - i - 1):
                if arr[j] > arr[j + 1]:
                    arr[j], arr[j + 1] = arr[j + 1], arr[j]
                    swapped = True
            # If no swaps happened, the list is already sorted
            if not swapped:
                break
        return arr

5.3d) Conclusions about Big O based on these runtimes:
All three algorithms are O(n^2), and my runtimes match that. Every time the list got
10 times bigger, the runtime grew by about 100 times (for example, selection sort went
from 0.0637 s at 1,000 items to 6.3891 s at 10,000 items). So Big O correctly predicts how each
algorithm scales as n grows. However, the three runtimes are not equal even though they share the
same Big O. Selection sort was the fastest, insertion sort was slower, and bubble sort was
the slowest. Big O ignores constant factors, such as how many comparisons and swaps each
algorithm does per step. Bubble sort swaps neighbors very often, while selection sort makes at
most one swap per pass. This shows that Big O tells us how an algorithm grows, but not exactly how
fast it runs, so two algorithms with the same Big O can still differ in practice.
